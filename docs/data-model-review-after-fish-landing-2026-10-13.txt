WHAT NOW WORKS IN MULTIPLAYER

Fish storage: fishing.catch.store validates an owned vessel and installed
catch hold, records individual specimens, and publishes fishing_hold updates.
Rebuilt ships hydrate those records. Fishing motion is separate, disposable
player presentation; it does not award inventory or money.

Landing: the existing quay pump runs its animation on participating clients.
In MP it does not remove fish locally. The owner submits fishing.catch.land
with vessel_id, operation_id and the IDs of the fish present when pumping began.
The server checks the operation owner, vessel, unloading status, berth,
mooring and minimum pumping time, and finds the requested lots in its holds.
It calculates NOK from its species catalog, mass and quality. Client prices
are ignored. The database transaction commits inventory removal, payment,
receipt, events and projections together. A rollback leaves all unchanged.

Published records:
  fishing_hold: vessel/hold capacity and remaining individual catch lots.
  fish_landing: owner's immutable sale receipt; operation, vessel, port,
                owner, mass_kg, value_nok and sold specimens.
  port_fish_landing: the same delivered batch available to port subscribers.
  landed_fish: consumed specimen identity, preventing re-storage after sale.

The port landing receipt is a delivered-batch history, NOT a complete mutable
shore warehouse with processing, stock consumption or NPC purchase budgets.
Payment credits the existing captains.marks database column, which stores NOK
and is the balance used by the live shipwright. The client fetches that balance
after acknowledgement. We have NOT migrated the whole game onto company money.

WHAT THE MODEL REVIEW FOUND

There are still TWO economic/vessel paths, not one finished unified model:

Live game:
  account/captain tables -> captain NOK balance -> legacy vessels rows with
  full brick_layout; reliable berth/operation/cargo/fishing projections;
  captain document still holds parts of local progression and contract state.

Native data lab:
  typed company/member/balance, immutable construction, company-owned vessel,
  cargo custody/slot, contract and transaction projections. Purchases, freight
  loading/unloading, arrival and settlement run through the authority. NPC and
  player companies use the same records. This is an isolated scratch world.

The lab is a useful foundation, but its company balances are not yet the live
shipwright/fish-landing balance. Calling both 'company finances' hides the gap.

RECOMMENDED NEXT IMPLEMENTATION ORDER

1. Map existing IDs and writers. Pick canonical account/company/vessel/item
   owners and preserve migration links. Define which records are public,
   nearby-only, company-private or owner-private.
2. Move live balances and vessel ownership onto the typed company model with
   a one-time transactional migration. Adapt shipwright and fish receipts to
   the same ledger. Test that old saves cannot restore spent currency.
3. Establish inventory custody/capacity as the common rule for containers,
   catch lots and movable equipment. Keep species, container paint, cargo
   destinations and trap preparation as typed details/references. Render the
   manifest; never infer durable custody from a mesh position.
4. Move real crane/freight and trap actions into these commands. Add canonical
   port facilities and server fish population rules. Keep visual operation
   playback separate from inventory and settlement.
5. Extend the existing native data lab with live-schema scenario adapters,
   invariants, event inspection and reconstruction. Do not create another
   disconnected demonstration schema or HTML inspector.

SIMULATIONS WE CAN RUN NOW

The existing lab already simulates purchase -> capacity-limited load ->
logical arrival -> unload -> freight settlement -> restart, without ship
physics. The new Go fishing test simulates catch storage -> moor -> start
unloading -> advance authoritative time -> land -> retry -> reconstruct.
Those are real authority handlers, not UI button scripts pretending to test.

Next scenarios should assert:
  - An item is in exactly one place; partial transfers conserve mass.
  - Slot/hold capacity follows a construction revision, including UGC builds.
  - Payment and custody commit together, or neither does.
  - Duplicate, stale, unauthorized and simultaneous commands cannot duplicate
    items, overfill a slot, double-pay, or spend another company's money.
  - Disconnect/reconnect during a crane or landing job gives the same result
    as staying connected; observers converge from snapshot plus events.
  - Two friends can operate one company's fleet under roles; NPC companies
    obey the same financial and cargo rules.
  - A fresh client reconstructs all durable contents and placed equipment
    from data at a committed event cursor.

REPLAY LIMITS TO KEEP HONEST

ReconstructAt requires the complete journal and a transaction-boundary cursor.
The startup authority cache restores only the most recent 20,000 events, so
historical export needs a database journal reader/checkpoint strategy.
Fish hold/landing receipts replay today. The entire live economy does not:
legacy captain balances and vessel SQL writes are not all journal projections.
Physics is intentionally outside this work. The missing work is canonical
records, command ownership and complete economic/custody events.
